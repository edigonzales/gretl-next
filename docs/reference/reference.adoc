= GRETL-Referenzdokumentation

Das Datenmanagement-Tool _GRETL_ wird für Datenimporte, Datenumbauten
(Modellumbauten) und Datenexporte eingesetzt. _GRETL_ führt Jobs aus, wobei
ein Job aus mehreren atomaren Tasks besteht. Damit ein Job vollständig
ausgeführt wurde, muss jeder zum Job gehörende Task erfolgreich ausgeführt
worden sein. Schlägt ein Task fehl, gilt auch der Job als fehlgeschlagen.

Ein Job besteht aus einem oder mehreren Tasks, die gemäss einem gerichteten
azyklischen Graphen (Directed Acyclic Graph; DAG) miteinander verknüpft sind.
Die Tasks werden im Gradle-Build-File konfiguriert.

Ein Job kann aus einer linearen Kette von Tasks bestehen:

[source,text]
----
Task 1 – Task 2 – Task 3 – Task n
----

Beispiel: Datenimport aus einer [.acronym]#INTERLIS#-Datei, Datenumbau und Datenexport
nach Shapefile.

Ein Job kann sich nach einem Task auf mehrere weitere Tasks verzweigen:

[source,text]
----
       – Task 2 – Task 3 – Task n
Task 1 –
       – Task 4 – Task 5 – Task m
----

Beispiel: Datenimport aus einer [.acronym]#INTERLIS#-Datei, anschliessender Datenumbau in
Zielschema 1 und ein zweiter Datenumbau in Zielschema 2.

Es ist auch möglich, dass zuerst mehrere Tasks unabhängig voneinander
ausgeführt werden, bevor ein weiterer Task beginnt:

[source,text]
----
Task 1 –
       – Task 3 – Task 4 – Task n
Task 2 –
----

== Systemanforderungen

Für GRETL Modular werden Java 17 und Gradle 7.6.4 verwendet. Die empfohlenen
Builds verwenden den eingecheckten Gradle Wrapper:

[source,bash]
----
./gradlew check
----

== Installation

GRETL Modular wird als Gradle-Plugin verwendet. Für einen Job werden die
benötigten Plugin-Repositories im +pluginManagement+-Block des Settings-Files
und das passende Plugin im Build-File konfiguriert.

Für lokale Entwicklung kann der aktuelle Snapshot aus dem Repository verwendet
werden. Veröffentlichte Versionen werden über das GRETL-Maven-Repository
bezogen.

== Kleines Beispiel

Das folgende Build-File führt SQL-Dateien gegen eine SQLite-Datenbank aus und
komprimiert anschliessend eine Datei:

[source,gradle,linenums]
----
plugins {
    id 'ch.so.agi.gretl'
}

import ch.so.agi.gretl.tasks.Gzip
import ch.so.agi.gretl.tasks.SqlExecutor

tasks.register('executeSql', SqlExecutor) {
    database 'jdbc:sqlite:build/example.db'
    sqlFiles 'sql/init.sql'
}

tasks.register('compressXml', Gzip) {
    dataFile 'data/input.xml'
    gzipFile layout.buildDirectory.file('out/input.xml.gz').get().asFile
}
----

== Ausführen

Ein Job wird im Verzeichnis mit seinem Gradle-Build ausgeführt:

[source,bash]
----
./gradlew
----

Alternativ kann ein Job aus einem beliebigen Verzeichnis mit +--project-dir+
gestartet werden:

[source,bash]
----
./gradlew --project-dir /pfad/zum/job
----

Zusätzliche Gradle-Properties können für parametrisierte Jobs übergeben
werden, zum Beispiel:

[source,bash]
----
./gradlew -Pdataset=Olten
----

=== Av2ch

Transformiert eine [.acronym]##INTERLIS##1-Transferdatei im kantonalen AV-DM01-Modell in das
Bundesmodell. Unterstützt werden die Sprachen _Deutsch_ und _Italienisch_ und
der Bezugsrahmen _LV95_. Getestet wurde der Task mit Daten aus den Kantonen
Solothurn, Glarus und Tessin. Weitere Informationen sind in der
Basisbibliothek link:https://github.com/sogis/av2ch[av2ch] zu finden.

Das Bundes-ITF hat denselben Namen wie das Kantons-ITF.

Aufgrund der sehr vielen Logging-Meldungen einer verwendeten Bibliothek wird
der +System.err+-Output nach +/dev/null+ umgeleitet. Die relevante Stelle ist
im link:https://github.com/sogis/av2ch/blob/master/src/main/java/ch/so/agi/av/Av2ch.java#L75[Quellcode]
dokumentiert.

Eine einzelne Datei kann mit +inputFiles+ transformiert werden:

[source,groovy]
----
tasks.register('transform', Av2ch) {
    inputFiles files('254900.itf')
    outputDirectory 'output'
}
----

Es können auch mehrere Dateien gleichzeitig transformiert werden:

[source,groovy]
----
tasks.register('transform', Av2ch) {
    inputFiles fileTree('.') {
        include '*.itf'
    }
    outputDirectory 'output'
}
----

=== Av2geobau

Av2geobau konvertiert eine [.acronym]#INTERLIS#-Transferdatei (ITF) in eine DXF-GeoBau-
Datei. Av2geobau funktioniert ohne Datenbank.

Die ITF-Datei muss dem Modell +DM01AVCH24LV95D+ entsprechen. Die Daten werden
nicht validiert.

Die Datenstruktur der DXF-Datei ist im Prinzip einfach: Die verschiedenen
Informationen aus dem Datenmodell DM01 werden in verschiedene DXF-Layer
abgebildet, zum Beispiel die begehbaren LFP1 in den Layer +01111+ oder die
Gebäude in den Layer +01211+.

Der Datenumbau ist nicht konfigurierbar.

[source,groovy]
----
tasks.register('av2geobau', Av2geobau) {
    itfFiles files('ch_254900.itf')
    dxfDirectory './out/'
}
----

Es können auch mehrere Dateien angegeben werden:

[source,groovy]
----
tasks.register('av2geobau', Av2geobau) {
    itfFiles fileTree('.') {
        include '*.itf'
    }
    dxfDirectory './out/'
}
----

=== Csv2Excel

Konvertiert eine CSV-Datei in eine Excel-Datei (+.xlsx+). Datentypen werden
anhand eines [.acronym]#INTERLIS#-Modells ermittelt. Fehlt das Modell, wird alles als Text
gespeichert. Die Daten werden vollständig im Speicher vorgehalten. Bei grossen
Dateien kann das zu Problemen führen. Falls die Datei +outputFile+ bereits
existiert, wird ein neues Sheet erstellt; die Datei wird nicht überschrieben.
Der Sheet-Name entspricht dem normalisierten Namen der CSV-Datei. Ein Fehler
wird gemeldet, falls der Sheet-Name bereits existiert.

[source,groovy]
----
tasks.register('convertData', Csv2Excel) {
    csvFile './20230124_sap_Gebaeude.csv'
    firstLineIsHeader true
    valueDelimiter null
    valueSeparator ';'
    encoding 'ISO-8859-1'
    models 'SO_HBA_Gebaeude_20230111'
    outputFile 'output.xlsx'
}
----

=== CsvValidator

Prüft eine CSV-Datei gegenüber einem [.acronym]#INTERLIS#-Modell. Der Task basiert auf dem
link:https://github.com/claeis/ilivalidator[ilivalidator]. Das Datenmodell darf
die OID nicht als +INTERLIS.UUIDOID+ modellieren.

Beispiele:

[source,groovy]
----
tasks.register('validate', CsvValidator) {
    models 'CsvModel'
    firstLineIsHeader true
    dataFiles 'data1.csv'
}
----

[source,groovy]
----
tasks.register('validateFahrzeugbestandCsv', CsvValidator) {
    models 'SO_MFK_Fahrzeugbestand_20250201'
    modeldir '../models/'
    firstLineIsHeader true
    dataFiles '../data/ch.so.mfk.fahrzeugbestand.csv'
    valueSeparator ';'
    valueDelimiter null
}
----

Falls die CSV-Datei eine Header-Zeile mit den Spaltennamen enthält, wird im
gegebenen Modell eine Klasse gesucht, welche die Header-Spaltennamen enthält.
Gross-/Kleinschreibung sowie optionale Spalten der Modell-Klasse werden
ignoriert. Wird keine solche Klasse gefunden, gilt das als Validierungsfehler.

Falls die CSV-Datei keine Header-Zeile enthält, wird im gegebenen Modell eine
Klasse mit derselben Anzahl Attribute gesucht. Wird keine solche Klasse
gefunden, gilt das als Validierungsfehler.

Die Prüfung mehrerer CSV-Dateien im selben Task kann zu Fehlermeldungen wie
+OID o3158 of object <Modelname>.<Topicname>.<Klassenname> already exists in ...+
führen. Beim Öffnen und Lesen einer CSV-Datei wird der interne OID-Zähler
zurückgesetzt. Deshalb kann pro Task nur eine CSV-Datei geprüft werden.

Ein Token kann in einem vorgelagerten Task abgerufen und für eine nachfolgende
Anfrage verwendet werden:

[source,groovy]
----
import groovy.json.JsonSlurper

def basicHeader = 'Basic ' + Base64.getEncoder()
    .encodeToString((clientId + ':' + clientSecret).getBytes())
def token = ''

tasks.register('getToken', Curl) {
    serverUrl 'https://auth.example.ch/oauth2/token'
    method MethodType.POST
    outputFile './token.json'
    expectedStatusCode 200
    data "grant_type=client_credentials&client_id=$clientId"
    headers([
        'Content-Type': 'application/x-www-form-urlencoded',
        Authorization: basicHeader
    ])

    doLast {
        def slurper = new JsonSlurper()
        def slurped = slurper.parseText(outputFile.get().asFile.text)
        if (slurped.access_token != null) {
            token = slurped.access_token
        }
        if (token.length() == 0) {
            throw new GradleException('Failed to retrieve access token')
        }
        println 'Length of access token is: ' + token.length()
    }
}

tasks.register('downloadJson', Curl) {
    dependsOn 'getToken'
    serverUrl 'https://obs.example.ch/rest/v4/docs.json?projects=83505'
    method MethodType.GET
    outputFile './data.json'
    expectedStatusCode 200
    headers([
        Authorization: providers.provider { 'Bearer ' + token }
    ])
}
----

=== Db2Db

Der Task +Db2Db+ ist prinzipiell eine 1:1-Datenkopie. Es findet kein
Datenumbau statt; Quell- und Zieltabelle haben jeweils identische Attribute.
In der Regel werden auf der Quellseite einfache SELECT-Queries ausgeführt und
die Resultate in Tabellen der Ziel-Datenbank eingefügt. Unter bestimmten
Bedingungen kann der Task auch für einen wenig komplexen Datenumbau verwendet
werden.

Die Queries können auf mehrere +.sql+-Dateien verteilt werden. Jede SQL-Datei
liefert genau ein Resultset zurück, das in die konfigurierte Zieltabelle
geschrieben wird. Der Task verarbeitet innerhalb einer Transaktion ein oder
mehrere Resultsets.

Die Reihenfolge der SQL-Dateien ist relevant. Alle SELECT-Statements werden in
einer Transaktion ausgeführt, damit ein konsistenter Datenstand gelesen wird.
Alle INSERT-Statements werden ebenfalls in einer Transaktion ausgeführt, damit
bei einem Fehler kein unvollständiger Import zurückbleibt.

Parameter innerhalb einer SQL-Datei werden mit der Syntax
+${paramName}+ verwendet:

[source,groovy]
----
def db_uri = 'jdbc:postgresql://localhost:54321/gretldemo'
def db_user = 'dmluser'
def db_pass = 'dmluser'

tasks.register('transferSomeData', Db2Db) {
    sourceDatabase db_uri, db_user, db_pass
    targetDatabase 'jdbc:sqlite:gretldemo.sqlite'
    sqlParameters([dataset: 'Olten'])
    transfer 'some.sql', 'albums_dest', true
}
----

Damit mit einer einzigen Task-Definition mehrere Datensätze verarbeitet werden
können, kann eine Liste von Parametern angegeben werden:

[source,groovy]
----
tasks.register('transferSomeData', Db2Db) {
    sourceDatabase db_uri, db_user, db_pass
    targetDatabase 'jdbc:sqlite:gretldemo.sqlite'
    sqlParameterSets([dataset: 'Olten'], [dataset: 'Grenchen'])
    transfer 'some.sql', 'albums_dest', true
}
----

Ein Transfer besteht aus einer SQL-Datei, dem Namen der Zieltabelle und der
Angabe, ob vor dem INSERT alle Datensätze gelöscht werden sollen. Optional
können Geometriespalten angegeben werden, um einen WKT-String in eine
PostGIS-Geometrie umzuwandeln:

[source,groovy]
----
transfer 'untersuchungseinheit.sql',
    'afu_qrcat_v1.onlinerisk_untersuchungseinheit',
    true,
    'geom:wkt:2056'
----

+geom+ ist der Name der verwendeten Geometriespalte. Ein SQL-Auszug zur
Erzeugung des WKT-Strings mittels Konkatenation:

[source,sql]
----
'Point(' || ue.koordinate_x::text || ' ' || ue.koordinate_y::text || ')' AS geom
----

Unterstützte Datenbanken sind PostgreSQL, SQLite, Oracle, Derby und DuckDB.

=== Gpkg2Dxf

Exportiert alle Tabellen einer GeoPackage-Datei in DXF-Dateien. Als Input wird
eine von _ili2gpkg_ erzeugte GeoPackage-Datei benötigt.

Es werden alle [.acronym]#INTERLIS#-Klassen exportiert. Der eigentliche SELECT-Befehl ist
komplexer, weil für das Layern der einzelnen DXF-Objekte das [.acronym]#INTERLIS#-
Metaattribut +!!@dxflayer="true"+ ausgelesen wird. Gibt es kein solches
Metaattribut, wird alles in den gleichen DXF-Layer (+default+) geschrieben.

Die DXF-Dateien sind +ISO-8859-1+ encodiert. Der Task sollte bei Bedarf noch
weiter verbessert werden.

[source,groovy]
----
tasks.register('gpkg2dxf', Gpkg2Dxf) {
    dataFile 'data.gpkg'
    outputDir './out/'
}
----

=== Gpkg2Shp

Exportiert alle Tabellen einer GeoPackage-Datei in Shapefiles. Als Input wird
eine von _ili2gpkg_ erzeugte GeoPackage-Datei benötigt.

Es werden alle [.acronym]#INTERLIS#-Klassen exportiert. Je nach den bei der Erstellung der
GeoPackage-Datei verwendeten Parametern muss die Query angepasst werden. Für
den vorgesehenen Anwendungsfall einfacher, flacher Modelle reicht eine Query
für alle Datensätze.

Die Shapefiles werden mit +UTF-8+ encodiert. Der frühere Standard
+ISO-8859-1+ funktioniert insbesondere in QGIS nicht immer korrekt mit
Umlauten.

[source,groovy]
----
tasks.register('gpkg2shp', Gpkg2Shp) {
    dataFile 'data.gpkg'
    outputDir './out/'
}
----

=== Ili2duckdbImportSchema

Erstellt die Tabellenstruktur in der DuckDB-Datenbank anhand eines [.acronym]#INTERLIS#-
Modells. Fremdschlüssel werden nicht unterstützt, weil die +ADD CONSTRAINT+-
Syntax nicht unterstützt wird. Es muss +--strokeArcs+ verwendet werden.
Räumliche Indizes von DuckDB sind noch rudimentär umgesetzt.

=== JsonValidator

Prüft eine JSON-Datei gegenüber einem [.acronym]#INTERLIS#-Modell. Der Task basiert auf
dem _ilivalidator_. Der verwendete JSON-Reader unterstützt viele
Sprachfeatures von [.acronym]#INTERLIS# und erwartet unter anderem +@type+, +@bid+, +@id+
und +@topic+. Für den aktuellen Anwendungsfall reicht die Information des
Typs; die übrigen Attribute und ein Top-Level-Array werden bei Bedarf vor der
Validierung ergänzt.

Ein strikter Modus zur Abbildung des ursprünglichen JSON-Reader-Verhaltens
kann später ergänzt werden.

[source,groovy]
----
tasks.register('validate', JsonValidator) {
    models 'Test2'
    dataFiles 'structAttr.json'
}
----

Beispiel für eine JSON-Datei:

[source,json]
----
{
    "@type": "Test2.Topic2.ClassA",
    "attrText": "line0",
    "attrStruct": {
        "@type": "Test2.Topic2.StructA",
        "attrText": "lineA"
    },
    "attrBag": [
        {
            "@type": "Test2.Topic2.StructA",
            "attrText": "li"
        },
        {
            "@type": "Test2.Topic2.StructA",
            "attrText": "lineC"
        }
    ],
    "attrTextList": ["lineDXXXX", "lineE"],
    "attrSurface": "POLYGON ((2460000 1045000, 2460001 1045000, 2460001 1045001, 2460000 1045001, 2460000 1045000))"
}
----

Das dazugehörige [.acronym]#INTERLIS#-Modell:

[source,interlis]
----
INTERLIS 2.4;

MODEL Test2 (de) AT "mailto:ceis@localhost" VERSION "20170703" =
    TOPIC Topic2 =
        STRUCTURE StructA =
            attrText : TEXT*3;
            attrInt : -1000 .. 1000;
        END StructA;

        CLASS ClassA =
            attrText : TEXT*60;
            attrStruct : StructA;
            attrBag : BAG OF StructA;
            attrTextList : LIST {0..*} OF TEXT*5;
            attrSurface : AREA WITH (STRAIGHTS, ARCS) VERTEX Coord2 WITHOUT OVERLAPS > 0.001;
        END ClassA;
    END Topic2;
END Test2.
----

=== SqlExecutor

Der +SqlExecutor+-Task dient dazu, Datenumbauten auszuführen. Er wird
allgemein verwendet, wenn der Umbau komplex ist, die Quell-Datenbank keine
PostgreSQL-Datenbank ist oder Quell- und Zielschema in derselben Datenbank
liegen.

In den ersten beiden Fällen werden Stagingtabellen beziehungsweise ein
Stagingschema benötigt, in welche ein vorheriger +Db2Db+-Task die Daten zuerst
1:1 schreibt. Der +SqlExecutor+-Task liest die Daten, baut sie um und schreibt
sie in das Zielschema. Die SQL-Anweisungen können in einer oder mehreren
SQL-Dateien liegen. Die Reihenfolge der Dateien ist relevant.

Neben Updates ganzer Tabellen unterstützt der Task auch Updates von Teilen
einer Tabelle. Parameter innerhalb einer SQL-Datei werden mit
+${paramName}+ geschrieben und beim Task konfiguriert. Unterstützte
Datenbanken sind PostgreSQL, SQLite, Oracle, Derby und DuckDB. Für weitere
Datenbanken muss der JDBC-Treiber als Abhängigkeit definiert werden.

[source,groovy]
----
def db_uri = 'jdbc:postgresql://localhost:54321/gretldemo'
def db_user = 'dmluser'
def db_pass = 'dmluser'

tasks.register('executeSomeSql', SqlExecutor) {
    database db_uri, db_user, db_pass
    sqlParameters([dataset: 'Olten'])
    sqlFiles 'demo.sql'
}
----

Mit einer einzigen Task-Definition können mehrere Datensätze verarbeitet
werden:

[source,groovy]
----
tasks.register('executeSomeSql', SqlExecutor) {
    database db_uri, db_user, db_pass
    sqlParameterSets([dataset: 'Olten'], [dataset: 'Grenchen'])
    sqlFiles 'demo.sql'
}
----
