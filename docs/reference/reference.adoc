= GRETL-Referenzdokumentation

Das Datenmanagement-Tool [.product]#GRETL# wird für Datenimporte, Datenumbauten
(Modellumbauten) und Datenexporte eingesetzt. [.product]#GRETL# führt Jobs aus, wobei
ein Job aus mehreren atomaren Tasks besteht. Damit ein Job vollständig
ausgeführt wurde, muss jeder zum Job gehörende Task erfolgreich ausgeführt
worden sein. Schlägt ein Task fehl, gilt auch der Job als fehlgeschlagen.

Ein Job besteht aus einem oder mehreren Tasks, die gemäss einem gerichteten
azyklischen Graphen (Directed Acyclic Graph; [.acronym]#DAG#) miteinander verknüpft sind.
Die Tasks werden im [.product]#Gradle#-Build-File konfiguriert.

Ein Job kann aus einer linearen Kette von Tasks bestehen:

[source,text]
----
Task 1 – Task 2 – Task 3 – Task n
----

Beispiel: Datenimport aus einer [.acronym]#INTERLIS#-Datei, Datenumbau und Datenexport
nach [.product]#Shapefile#.

Ein Job kann sich nach einem Task auf mehrere weitere Tasks verzweigen:

[source,text]
----
       – Task 2 – Task 3 – Task n
Task 1 –
       – Task 4 – Task 5 – Task m
----

Beispiel: Datenimport aus einer [.acronym]#INTERLIS#-Datei, anschliessender Datenumbau in
Zielschema 1 und ein zweiter Datenumbau in Zielschema 2.

Es ist auch möglich, dass zuerst mehrere Tasks unabhängig voneinander
ausgeführt werden, bevor ein weiterer Task beginnt:

[source,text]
----
Task 1 –
       – Task 3 – Task 4 – Task n
Task 2 –
----

== Systemanforderungen

Für [.product]#GRETL# Modular werden [.product]#Java# 17 und [.product]#Gradle# 7.6.4 verwendet. Die empfohlenen
Builds verwenden den eingecheckten [.product]#Gradle# Wrapper:

[source,bash]
----
./gradlew check
----

== Installation

[.product]#GRETL# Modular wird als [.product]#Gradle#-Plugin verwendet. Für einen Job werden die
benötigten Plugin-Repositories im [.dsl-method]#`pluginManagement`#-Block des Settings-Files
und das passende Plugin im Build-File konfiguriert.

Für lokale Entwicklung kann der aktuelle Snapshot aus dem Repository verwendet
werden. Veröffentlichte Versionen werden über das [.product]#GRETL#-[.product]#Maven#-Repository
bezogen.

== Kleines Beispiel

Das folgende Build-File führt [.acronym]#SQL#-Dateien gegen eine [.product]#SQLite#-Datenbank aus und
komprimiert anschliessend eine Datei:

[source,gradle,linenums]
----
plugins {
    id 'ch.so.agi.gretl'
}

import ch.so.agi.gretl.tasks.Gzip
import ch.so.agi.gretl.tasks.SqlExecutor

tasks.register('executeSql', SqlExecutor) {
    database 'jdbc:sqlite:build/example.db'
    sqlFiles 'sql/init.sql'
}

tasks.register('compressXml', Gzip) {
    dataFile 'data/input.xml'
    gzipFile layout.buildDirectory.file('out/input.xml.gz').get().asFile
}
----

== Ausführen

Ein Job wird im Verzeichnis mit seinem [.product]#Gradle#-Build ausgeführt:

[source,bash]
----
./gradlew
----

Alternativ kann ein Job aus einem beliebigen Verzeichnis mit [.cli-option]#`--project-dir`#
gestartet werden:

[source,bash]
----
./gradlew --project-dir /pfad/zum/job
----

Zusätzliche [.product]#Gradle#-Properties können für parametrisierte Jobs übergeben
werden, zum Beispiel:

[source,bash]
----
./gradlew -Pdataset=Olten
----

== Tasks

Die folgenden Abschnitte bestimmen die redaktionelle Reihenfolge und erklären
die Aufgabe der einzelnen Task-Typen. Die jeweils aktuelle Tabelle der
öffentlichen [.acronym]#DSL#-Methoden wird aus den Task-Annotationen und Javadocs erzeugt.

Die Beispiele setzen voraus, dass die verwendeten Task-Klassen im Build-File
importiert wurden, zum Beispiel mit [.code-fragment]#`import ch.so.agi.gretl.tasks.*`#.

.Hinweis zur Schreibweise
[NOTE]
====
Die Spalte «[.acronym]#DSL#-Methode» zeigt die Parametertypen der öffentlichen Methode.
[.java-type]##`String`##s werden in [.product]#Groovy# in Anführungszeichen angegeben, Wahrheitswerte und
Zahlen ohne Anführungszeichen.

Bei [.java-type]#`Object`# [.parameter]#`path`# kann ein Pfad direkt als String geschrieben werden,
zum Beispiel [.code-fragment]#`dataFile 'fubar.xtf'`#; [.product]#Gradle#-Ausdrücke wie
[.code-fragment]#`dataFile file('fubar.xtf')`# werden ebenfalls akzeptiert.
[.java-type]#`Object\...`# [.parameter]#`paths`# erlaubt einen oder mehrere Pfade sowie
[.product]#Gradle#-Dateisammlungen wie [.dsl-method]#`files(\...)`# oder
[.dsl-method]#`fileTree(\...)`#.
====

=== Av2ch

Transformiert eine [.acronym]#INTERLIS#-1-Transferdatei im kantonalen [.acronym]#AV#-[.domain-id]#`DM01`#-Modell in das
Bundesmodell. Unterstützt werden die Sprachen _Deutsch_ und _Italienisch_ und
der Bezugsrahmen [.domain-id]#`LV95`#. Getestet wurde der Task mit Daten aus den Kantonen
Solothurn, Glarus und Tessin. Weitere Informationen sind in der
Basisbibliothek [.product]#link:https://github.com/sogis/av2ch[av2ch]# zu finden.

Das Bundes-[.acronym]#ITF# hat denselben Namen wie das Kantons-[.acronym]#ITF#.

Aufgrund der sehr vielen Logging-Meldungen einer verwendeten Bibliothek wird
der [.code-fragment]#`System.err`#-Output nach [.path]#`/dev/null`# umgeleitet. Die relevante Stelle ist
im link:https://github.com/sogis/av2ch/blob/master/src/main/java/ch/so/agi/av/Av2ch.java#L75[Quellcode]
dokumentiert.

Eine einzelne Datei kann mit [.dsl-method]#`inputFiles`# transformiert werden:

[source,groovy]
----
tasks.register('transform', Av2ch) {
    inputFiles files('254900.itf')
    outputDirectory 'output'
}
----

Es können auch mehrere Dateien gleichzeitig transformiert werden:

[source,groovy]
----
tasks.register('transform', Av2ch) {
    inputFiles fileTree('.') {
        include '*.itf'
    }
    outputDirectory 'output'
}
----

=== Av2geobau

[.task-type]#`Av2geobau`# konvertiert eine [.acronym]#INTERLIS#-Transferdatei ([.acronym]#ITF#) in eine
[.acronym]#DXF#-[.product]#GeoBau#-Datei. [.task-type]#`Av2geobau`# funktioniert ohne Datenbank.

Die [.acronym]#ITF#-Datei muss dem Modell [.domain-id]#`DM01AVCH24LV95D`# entsprechen. Die Daten werden
nicht validiert.

Die Datenstruktur der [.acronym]#DXF#-Datei ist im Prinzip einfach: Die verschiedenen
Informationen aus dem Datenmodell [.domain-id]#`DM01`# werden in verschiedene [.acronym]#DXF#-Layer
abgebildet, zum Beispiel die begehbaren [.domain-id]#`LFP1`# in den Layer [.domain-id]#`01111`# oder die
Gebäude in den Layer [.domain-id]#`01211`#.

Der Datenumbau ist nicht konfigurierbar.

[source,groovy]
----
tasks.register('av2geobau', Av2geobau) {
    itfFiles files('ch_254900.itf')
    dxfDirectory './out/'
}
----

Es können auch mehrere Dateien angegeben werden:

[source,groovy]
----
tasks.register('av2geobau', Av2geobau) {
    itfFiles fileTree('.') {
        include '*.itf'
    }
    dxfDirectory './out/'
}
----

=== Csv2Excel

Konvertiert eine [.acronym]#CSV#-Datei in eine [.product]#Excel#-Datei ([.file-ext]#`.xlsx`#). Datentypen werden
anhand eines [.acronym]#INTERLIS#-Modells ermittelt. Fehlt das Modell, wird alles als Text
gespeichert. Die Daten werden vollständig im Speicher vorgehalten. Bei grossen
Dateien kann das zu Problemen führen. Falls die Datei [.dsl-method]#`outputFile`# bereits
existiert, wird ein neues Sheet erstellt; die Datei wird nicht überschrieben.
Der Sheet-Name entspricht dem normalisierten Namen der [.acronym]#CSV#-Datei. Ein Fehler
wird gemeldet, falls der Sheet-Name bereits existiert.

[source,groovy]
----
tasks.register('convertData', Csv2Excel) {
    csvFile './20230124_sap_Gebaeude.csv'
    firstLineIsHeader true
    valueDelimiter null
    valueSeparator ';'
    encoding 'ISO-8859-1'
    models 'SO_HBA_Gebaeude_20230111'
    outputFile 'output.xlsx'
}
----

=== CsvImport

Daten aus einer [.acronym]#CSV#-Datei werden in eine bestehende Datenbanktabelle
importiert.

Die Tabelle kann weitere Spalten enthalten, die in der [.acronym]#CSV#-Datei nicht
vorkommen. Sie müssen aber [.literal]#`NULLable`# sein oder einen Default-Wert definiert
haben.

Geometriespalten können nicht importiert werden. Die Gross-/Kleinschreibung
der [.acronym]#CSV#-Spaltennamen wird für die Zuordnung zu den [.acronym]#DB#-Spalten ignoriert.

[source,groovy]
----
def db_uri = 'jdbc:postgresql://localhost:54321/gretldemo'
def db_user = 'dmluser'
def db_pass = 'dmluser'

tasks.register('csvimport', CsvImport) {
    database db_uri, db_user, db_pass
    schemaName 'csvimport'
    tableName 'importdata'
    firstLineIsHeader true
    dataFile 'data1.csv'
}
----

=== CsvValidator

Prüft eine [.acronym]#CSV#-Datei gegenüber einem [.acronym]#INTERLIS#-Modell. Der Task basiert auf dem
[.product]#link:https://github.com/claeis/ilivalidator[ilivalidator]#. Das Datenmodell darf
die [.acronym]#OID# nicht als [.domain-id]#`INTERLIS.UUIDOID`# modellieren.

Beispiele:

[source,groovy]
----
tasks.register('validate', CsvValidator) {
    models 'CsvModel'
    firstLineIsHeader true
    dataFiles 'data1.csv'
}
----

[source,groovy]
----
tasks.register('validateFahrzeugbestandCsv', CsvValidator) {
    models 'SO_MFK_Fahrzeugbestand_20250201'
    modeldir '../models/'
    firstLineIsHeader true
    dataFiles '../data/ch.so.mfk.fahrzeugbestand.csv'
    valueSeparator ';'
    valueDelimiter null
}
----

Falls die [.acronym]#CSV#-Datei eine Header-Zeile mit den Spaltennamen enthält, wird im
gegebenen Modell eine Klasse gesucht, welche die Header-Spaltennamen enthält.
Gross-/Kleinschreibung sowie optionale Spalten der Modell-Klasse werden
ignoriert. Wird keine solche Klasse gefunden, gilt das als Validierungsfehler.

Falls die [.acronym]#CSV#-Datei keine Header-Zeile enthält, wird im gegebenen Modell eine
Klasse mit derselben Anzahl Attribute gesucht. Wird keine solche Klasse
gefunden, gilt das als Validierungsfehler.

Die Prüfung mehrerer [.acronym]#CSV#-Dateien im selben Task kann zu Fehlermeldungen wie
[.code-fragment]#`OID o3158 of object <Modelname>.<Topicname>.<Klassenname> already exists in ...`#
führen. Beim Öffnen und Lesen einer [.acronym]#CSV#-Datei wird der interne [.acronym]#OID#-Zähler
zurückgesetzt. Deshalb kann pro Task nur eine [.acronym]#CSV#-Datei geprüft werden.

Ein Token kann in einem vorgelagerten Task abgerufen und für eine nachfolgende
Anfrage verwendet werden:

[source,groovy]
----
import groovy.json.JsonSlurper

def basicHeader = 'Basic ' + Base64.getEncoder()
    .encodeToString((clientId + ':' + clientSecret).getBytes())
def token = ''

tasks.register('getToken', Curl) {
    serverUrl 'https://auth.example.ch/oauth2/token'
    method MethodType.POST
    outputFile './token.json'
    expectedStatusCode 200
    data "grant_type=client_credentials&client_id=$clientId"
    headers([
        'Content-Type': 'application/x-www-form-urlencoded',
        Authorization: basicHeader
    ])

    doLast {
        def slurper = new JsonSlurper()
        def slurped = slurper.parseText(outputFile.get().asFile.text)
        if (slurped.access_token != null) {
            token = slurped.access_token
        }
        if (token.length() == 0) {
            throw new GradleException('Failed to retrieve access token')
        }
        println 'Length of access token is: ' + token.length()
    }
}

tasks.register('downloadJson', Curl) {
    dependsOn 'getToken'
    serverUrl 'https://obs.example.ch/rest/v4/docs.json?projects=83505'
    method MethodType.GET
    outputFile './data.json'
    expectedStatusCode 200
    headers([
        Authorization: providers.provider { 'Bearer ' + token }
    ])
}
----

=== Db2Db

Der Task [.task-type]#`Db2Db`# ist prinzipiell eine 1:1-Datenkopie. Es findet kein
Datenumbau statt; Quell- und Zieltabelle haben jeweils identische Attribute.
In der Regel werden auf der Quellseite einfache [.code-fragment]#`SELECT`#-Queries ausgeführt und
die Resultate in Tabellen der Ziel-Datenbank eingefügt. Unter bestimmten
Bedingungen kann der Task auch für einen wenig komplexen Datenumbau verwendet
werden.

Die Queries können auf mehrere [.file-ext]#`.sql`#-Dateien verteilt werden. Jede [.acronym]#SQL#-Datei
liefert genau ein Resultset zurück, das in die konfigurierte Zieltabelle
geschrieben wird. Der Task verarbeitet innerhalb einer Transaktion ein oder
mehrere Resultsets.

Die Reihenfolge der [.acronym]#SQL#-Dateien ist relevant. Alle [.code-fragment]#`SELECT`#-Statements werden in
einer Transaktion ausgeführt, damit ein konsistenter Datenstand gelesen wird.
Alle [.code-fragment]#`INSERT`#-Statements werden ebenfalls in einer Transaktion ausgeführt, damit
bei einem Fehler kein unvollständiger Import zurückbleibt.

Parameter innerhalb einer [.acronym]#SQL#-Datei werden mit der Syntax
[.placeholder]#`${paramName}`# verwendet:

[source,groovy]
----
def db_uri = 'jdbc:postgresql://localhost:54321/gretldemo'
def db_user = 'dmluser'
def db_pass = 'dmluser'

tasks.register('transferSomeData', Db2Db) {
    sourceDatabase db_uri, db_user, db_pass
    targetDatabase 'jdbc:sqlite:gretldemo.sqlite'
    sqlParameters([dataset: 'Olten'])
    transfer 'some.sql', 'albums_dest', true
}
----

Damit mit einer einzigen Task-Definition mehrere Datensätze verarbeitet werden
können, kann eine Liste von Parametern angegeben werden:

[source,groovy]
----
tasks.register('transferSomeData', Db2Db) {
    sourceDatabase db_uri, db_user, db_pass
    targetDatabase 'jdbc:sqlite:gretldemo.sqlite'
    sqlParameterSets([dataset: 'Olten'], [dataset: 'Grenchen'])
    transfer 'some.sql', 'albums_dest', true
}
----

Ein Transfer besteht aus einer [.acronym]#SQL#-Datei, dem Namen der Zieltabelle und der
Angabe, ob vor dem [.code-fragment]#`INSERT`# alle Datensätze gelöscht werden sollen. Optional
können Geometriespalten angegeben werden, um einen [.acronym]#WKT#-String in eine
[.product]#PostGIS#-Geometrie umzuwandeln:

[source,groovy]
----
transfer 'untersuchungseinheit.sql',
    'afu_qrcat_v1.onlinerisk_untersuchungseinheit',
    true,
    'geom:wkt:2056'
----

[.domain-id]#`geom`# ist der Name der verwendeten Geometriespalte. Ein [.acronym]#SQL#-Auszug zur
Erzeugung des [.acronym]#WKT#-Strings mittels Konkatenation:

[source,sql]
----
'Point(' || ue.koordinate_x::text || ' ' || ue.koordinate_y::text || ')' AS geom
----

Unterstützte Datenbanken sind [.product]#PostgreSQL#, [.product]#SQLite#, [.product]#Oracle#, [.product]#Derby# und [.product]#DuckDB#.

=== Gpkg2Dxf

Exportiert alle Tabellen einer [.product]#GeoPackage#-Datei in [.acronym]#DXF#-Dateien. Als Input wird
eine von [.product]#ili2gpkg# erzeugte [.product]#GeoPackage#-Datei benötigt.

Es werden alle [.acronym]#INTERLIS#-Klassen exportiert. Der eigentliche [.code-fragment]#`SELECT`#-Befehl ist
komplexer, weil für das Layern der einzelnen [.acronym]#DXF#-Objekte das [.acronym]#INTERLIS#-
Metaattribut [.code-fragment]#`!!@dxflayer="true"`# ausgelesen wird. Gibt es kein solches
Metaattribut, wird alles in den gleichen [.acronym]#DXF#-Layer ([.literal]#`default`#) geschrieben.

Die [.acronym]#DXF#-Dateien sind [.literal]#`ISO-8859-1`# encodiert. Der Task sollte bei Bedarf noch
weiter verbessert werden.

[source,groovy]
----
tasks.register('gpkg2dxf', Gpkg2Dxf) {
    dataFile 'data.gpkg'
    outputDir './out/'
}
----

=== Gpkg2Shp

Exportiert alle Tabellen einer [.product]#GeoPackage#-Datei in [.product]##Shapefile##s. Als Input wird
eine von [.product]#ili2gpkg# erzeugte [.product]#GeoPackage#-Datei benötigt.

Es werden alle [.acronym]#INTERLIS#-Klassen exportiert. Je nach den bei der Erstellung der
[.product]#GeoPackage#-Datei verwendeten Parametern muss die Query angepasst werden. Für
den vorgesehenen Anwendungsfall einfacher, flacher Modelle reicht eine Query
für alle Datensätze.

Die [.product]##Shapefile##s werden mit [.literal]#`UTF-8`# encodiert. Der frühere Standard
[.literal]#`ISO-8859-1`# funktioniert insbesondere in [.product]#QGIS# nicht immer korrekt mit
Umlauten.

[source,groovy]
----
tasks.register('gpkg2shp', Gpkg2Shp) {
    dataFile 'data.gpkg'
    outputDir './out/'
}
----

=== GpkgExport

Daten aus einer bestehenden Datenbanktabelle werden in eine [.product]#GeoPackage#-Datei
exportiert.

Beispiele:

[source,groovy]
----
def db_uri = 'jdbc:postgresql://localhost:54321/gretldemo'
def db_user = 'dmluser'
def db_pass = 'dmluser'

tasks.register('gpkgexport', GpkgExport) {
    database db_uri, db_user, db_pass
    schemaName 'gpkgexport'
    srcTableName 'exportdata'

=== JsonValidator

Prüft eine [.acronym]#JSON#-Datei gegenüber einem [.acronym]#INTERLIS#-Modell. Der Task basiert auf
dem [.product]#ilivalidator#. Der verwendete [.acronym]#JSON#-Reader unterstützt viele

und [.domain-id]#`@topic`#. Für den aktuellen Anwendungsfall reicht die Information des

Validierung ergänzt.

Ein strikter Modus zur Abbildung des ursprünglichen [.acronym]#JSON#-Reader-Verhaltens
kann später ergänzt werden.

[source,groovy]
----
tasks.register('validate', JsonValidator) {
    models 'Test2'
    dataFiles 'structAttr.json'
}
----

Beispiel für eine [.acronym]#JSON#-Datei:

[source,json]
----
{
    "@type": "Test2.Topic2.ClassA",
    "attrText": "line0",
    "attrStruct": {
        "@type": "Test2.Topic2.StructA",
        "attrText": "lineA"
    },
    "attrBag": [
        {
            "@type": "Test2.Topic2.StructA",
            "attrText": "li"
        },
        {
            "@type": "Test2.Topic2.StructA",
            "attrText": "lineC"
        }
    ],
    "attrTextList": ["lineDXXXX", "lineE"],
    "attrSurface": "POLYGON ((2460000 1045000, 2460001 1045000, 2460001 1045001, 2460000 1045001, 2460000 1045000))"
}
----

Das dazugehörige [.acronym]#INTERLIS#-Modell:

[source,interlis]
----
INTERLIS 2.4;

MODEL Test2 (de) AT "mailto:ceis@localhost" VERSION "20170703" =
    TOPIC Topic2 =
        STRUCTURE StructA =
            attrText : TEXT*3;
            attrInt : -1000 .. 1000;
        END StructA;

        CLASS ClassA =
            attrText : TEXT*60;
            attrStruct : StructA;
            attrBag : BAG OF StructA;
            attrTextList : LIST {0..*} OF TEXT*5;
            attrSurface : AREA WITH (STRAIGHTS, ARCS) VERTEX Coord2 WITHOUT OVERLAPS > 0.001;
        END ClassA;
    END Topic2;
END Test2.

Attributtypen werden nicht berücksichtigt. Wird keine solche Klasse gefunden,
gilt das als Validierungsfehler.

Die Prüfung mehrerer [.product]##Shapefile##s im selben Task kann zu Fehlermeldungen wie
[.code-fragment]#`OID o3158 of object <Modelname>.<Topicname>.<Klassenname> already exists in ...`#
führen. Beim Öffnen und Lesen eines [.product]##Shapefile##s wird der interne [.acronym]#OID#-Zähler
zurückgesetzt. Deshalb kann pro Task nur ein [.product]#Shapefile# geprüft werden.

[source,groovy]
----
tasks.register('validate', ShpValidator) {
    models 'ShpModel'
    dataFiles 'data.shp'
}
----

=== SqlExecutor

Der [.task-type]#`SqlExecutor`#-Task dient dazu, Datenumbauten auszuführen. Er wird
allgemein verwendet, wenn der Umbau komplex ist, die Quell-Datenbank keine
[.product]#PostgreSQL#-Datenbank ist oder Quell- und Zielschema in derselben Datenbank
liegen.

In den ersten beiden Fällen werden Stagingtabellen beziehungsweise ein
Stagingschema benötigt, in welche ein vorheriger [.task-type]#`Db2Db`#-Task die Daten zuerst
1:1 schreibt. Der [.task-type]#`SqlExecutor`#-Task liest die Daten, baut sie um und schreibt
sie in das Zielschema. Die [.acronym]#SQL#-Anweisungen können in einer oder mehreren
[.acronym]#SQL#-Dateien liegen. Die Reihenfolge der Dateien ist relevant.

Neben Updates ganzer Tabellen unterstützt der Task auch Updates von Teilen
einer Tabelle. Parameter innerhalb einer [.acronym]#SQL#-Datei werden mit
[.placeholder]#`${paramName}`# geschrieben und beim Task konfiguriert. Unterstützte
Datenbanken sind [.product]#PostgreSQL#, [.product]#SQLite#, [.product]#Oracle#, [.product]#Derby# und [.product]#DuckDB#. Für weitere
Datenbanken muss der [.acronym]#JDBC#-Treiber als Abhängigkeit definiert werden.

[source,groovy]
----
def db_uri = 'jdbc:postgresql://localhost:54321/gretldemo'
def db_user = 'dmluser'
def db_pass = 'dmluser'

tasks.register('executeSomeSql', SqlExecutor) {
    database db_uri, db_user, db_pass
    sqlParameters([dataset: 'Olten'])
    sqlFiles 'demo.sql'
}
----

Mit einer einzigen Task-Definition können mehrere Datensätze verarbeitet
werden:

[source,groovy]
----
tasks.register('executeSomeSql', SqlExecutor) {
    database db_uri, db_user, db_pass
    sqlParameterSets([dataset: 'Olten'], [dataset: 'Grenchen'])
    sqlFiles 'demo.sql'
}
----

=== XslTransformer

Transformiert eine oder mehrere [.acronym]#XML#-Dateien mit einer [.acronym]#XSLT#-Transformation.
Mit [.dsl-method]#`xslResource`# wird eine Stylesheet-Ressource aus dem Klassenpfad verwendet;
mit [.dsl-method]#`xslFile`# kann eine lokale Datei angegeben werden.

[source,groovy]
----
tasks.register('transform', XslTransformer) {
    xslResource 'eCH0132_to_SO_AGI_SGV_Meldungen_20221109.xsl'
    xmlFiles 'MeldungAnGeometer_G-0111102_20221103_145001.xml'
    outDirectory '.'
}
----

[source,groovy]
----
tasks.register('transform', XslTransformer) {
    xslFile 'path/to/eCH0132_to_SO_AGI_SGV_Meldungen_20221109.xsl'
    xmlFiles 'MeldungAnGeometer_G-0111102_20221103_145001.xml'
    outDirectory '.'
}
----

Es können auch mehrere [.acronym]#XML#-Dateien angegeben werden:

[source,groovy]
----
tasks.register('transform', XslTransformer) {
    xslResource 'eCH0132_to_SO_AGI_SGV_Meldungen_20221109.xsl'
    xmlFiles fileTree('.') {
        include '*.xml'
    }
    outDirectory '.'
}
----
