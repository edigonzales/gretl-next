= Combined `gretl-core` and `gretl-geotools` tests

The individual Core and GeoTools TestKit suites are necessary but do not prove
that both plugins can configure and execute in one real consumer build. The
internal `gretl-combined-tests` project owns that proof without becoming a
production or published module.

== Classpath and execution modes

The source suite writes a deterministic absolute classpath file at
`gretl-combined-tests/build/combined-plugin-classpath/classpath.txt`. It contains
the Core and GeoTools plugin artifacts and their required plugin runtime
dependencies. Host JUnit and GeoTools reader libraries are kept on the test
JVM only; validation rejects test-support, host assertion, source and Javadoc
artifacts from the child-build classpath.

The `PLUGIN_CLASSPATH` executor passes that file to Gradle TestKit explicitly.
The published suite uses the same test classes with `PUBLISHED_ARTIFACT` and
resolves both modern plugin markers from the isolated
`build/published-test/maven-repo`. There is no source-classpath fallback in
published mode.

== Boundary and pipeline

Core and GeoTools remain independent plugins and register distinct shared
services. GeoTools processing stays in its classloader-isolated worker; raw
GeoTools libraries do not enter the consumer buildscript classloader.

The primary canary is a real Gradle pipeline:

`XslTransformer -> RasterReclassify -> Gzip`

The XSLT creates a deterministic ESRI ASCII Grid. The raster task reads its
input through a `Provider<RegularFile>`, writes a GeoTIFF in LV95 (EPSG:2056),
and Gzip consumes the GeoTIFF output through another provider. These declared
inputs and outputs infer task dependencies without manual `dependsOn` calls.
Assertions inspect grid dimensions, values, CRS, no-data and the byte-exact
GZIP payload.

== Lifecycle coverage

The suite covers the Groovy DSL, both plugin application orders,
up-to-date invalidation, configuration-cache reuse, repeated builds, failure
propagation and a mixed core-only/GeoTools-only/mixed multi-project consumer.
Each test task uses one bounded TestKit user home, clears it before execution,
and removes it in a finalizer after execution. This prevents one Gradle cache
per temporary consumer project from accumulating on the host.

Each TestKit build receives the explicit daemon JVM argument
`-Dorg.gradle.jvmargs=-Xmx768m -XX:MaxMetaspaceSize=512m`. The TestKit daemon is
expected because TestKit executes through the Gradle Tooling API; setting
`-Dorg.gradle.daemon=false` does not remove that Tooling API process. Raw
`-Xmx` options in `GRADLE_OPTS` are intentionally not used for this purpose,
because `GRADLE_OPTS` configures the Gradle client JVM. The default can be
overridden for diagnostics with
`-PgretlTestKitJvmArgs="-Xmx1g -XX:MaxMetaspaceSize=768m"`.

Run the gates locally with:

`./gradlew :gretl-combined-tests:test`

`./gradlew :gretl-combined-tests:publishedArtifactTest`

`./gradlew :gretl-combined-tests:combinedConfigurationCacheTest`

`./gradlew coreGeoToolsCombinedTest`

CI runs the combined gate before snapshot publication and uploads the regular
reports, plus TestKit/classpath diagnostics when the gate fails. This suite is
specific to `gretl-next`; it does not migrate or reuse jobs from `gretljobs`.
